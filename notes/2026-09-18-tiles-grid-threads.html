Tiles, Grid, Threads

Four different things get called "the shape" around a cuTile kernel, and they are not the same shape. The data is a tensor, of any rank. The unit of work is a tile, ranks 0 to 6. The fleet is the grid, exactly three axes. Underneath sit thread blocks, warps, and threads, which cuTile hides from you on purpose. This note keeps the four apart, on the GPU side and on the host side, with a figure you can poke at. It assumes you know CUDA basics, so it starts from the CUDA kernel you already know and gives every term its CUDA cousin. Every quoted line comes from the repo's source or its book, cited by file and line; the GPU pod is stopped, so nothing here needed a new run.

Coming from CUDA

The book puts the two programming models side by side. Same job, vector addition, written the way you know it and the way cuTile wants it (cutile-book/guide/useful-mental-models.md:9-31, verbatim).

CUDA C++: one thread per element
__global__ void add(float* a, float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        c[i] = a[i] + b[i];
    }
}
cuTile: one program per tile
#[cutile::entry()]
fn add<const S: [i32; 2]>(
    c: &mut Tensor<f32, S>,
    a: &Tensor<f32, { [-1, -1] }>,
    b: &Tensor<f32, { [-1, -1] }>,
) {
    let tile_a = a.load_like(c);
    let tile_b = b.load_like(c);
    c.store(tile_a + tile_b);
}

Three things from the left side are gone on the right. The index arithmetic is gone, because the tile is the index: each program gets the sub-tensor it owns and never computes an offset. The guard if (i < n) is gone, because the partial edge tile is handled by padding on load and clipping on store. And blockDim and threadIdx are gone for good, because the host launches every program with a block size of one and the compiler decides how many real threads run it. The book's own summary: "The kernel describes what happens to one tile-shaped region. The compiler and runtime map that work onto CUDA execution units." (useful-mental-models.md:33).

What stays is the shape of everything around the kernel: a grid with three axes, a block index to read, streams to queue work on, a toolchain that ends in a cubin. The table is the dictionary; the rest of the note is the fine print.

Three axes, and why

The five-axis experiment, .grid((2, 2, 1, 1, 1)) with program_id(3) and program_id(4), fails in three different places, and each place is a different layer saying the same thing.

rustcThe launcher method takes a three-tuple and nothing else. That is a type, checked before any GPU exists:

// cutile/src/tile_kernel.rs:1352, the TileKernel trait
fn grid(self, grid: (u32, u32, u32)) -> Self;

hostWhen the grid is inferred from a partition instead, the host arithmetic has a rank arm for 1, 2, and 3 and one message for everything else: Mutable tensor must be at most rank 3. (the last arm of partition_launch_grid, cutile/src/tensor.rs:839).

Read that message slowly, because both words carry weight. "Mutable" means the &mut Tensor parameter, the output you write to, which is the only tensor that has to be partitioned on the host. "Rank" is the number of axes. The output is capped at three axes because the grid is derived from it one axis at a time, tensor axis k to grid axis k, so that every program owns a disjoint tile; a fourth tensor axis would need a fourth grid axis, and dim3 has none. Read-only inputs are not under this cap: they are passed whole and cut into tiles inside the kernel, so they never touch the grid. A 4-D output gets reshaped to 3-D on the host first, folding two axes into one, which is the same trick you would use in CUDA to fit a 4-D problem into blockIdx.

GPUInside the kernel, program_id(axis) is plain Rust that picks one component of a three-tuple, and its doc comment ends with "Axes above 2 fail a device assertion" (cutile/src/_core.rs:1610-1633). The first note's Tile IR dump shows that assertion as assert .., "program_id: axis must be 0, 1, or 2".

siliconUnder all three, the machine code reads exactly three block-index registers, SR_CTAID.X, .Y, and .Z, and no fourth one exists. The SASS excerpt from the first note has all three reads.

So the three is a property of the grid, the fleet of programs. It is not a property of tensors. A tensor has whatever rank you gave it, and the table below is the honest list of which limit lives where.

Four things called "the shape"

The grid is not a property of the tensor. It is a property of the pairing of a tensor with a tile shape, which is why .partition([32, 64]) is the call that creates it, and why a tensor on its own tells you nothing about how many programs will run. Each row below is one of the four things, in the book's own words.

the Rust that does this
// cutile/src/tensor.rs:798-841, shortened
fn partition_launch_grid(shape: &[i32], partition_shape: &[usize])
    -> Result<(u32, u32, u32), Error> {
    if shape.iter().any(|&d| d <= 0) { /* "Shape dimensions must be positive, got {shape:?}." */ }
    if partition_shape.len() != shape.len() { /* "Partition rank .. does not match tensor rank .." */ }
    if partition_shape.contains(&0) { /* "Partition dimensions must be positive, got .." */ }
    let axis = |i: usize| -> Result<u32, Error> {
        let extent = shape[i] as u32;
        let tile = u32::try_from(partition_shape[i])?;
        Ok(extent.div_ceil(tile))
    };
    match shape.len() {
        1 => Ok((axis(0)?, 1, 1)),
        2 => Ok((axis(0)?, axis(1)?, 1)),
        3 => Ok((axis(0)?, axis(1)?, axis(2)?)),
        _ => tensor_error_result("Mutable tensor must be at most rank 3."),
    }
}

Two guards against over-generalising. First, a grid axis is not a loop. In the GEMM example the output z is partitioned [bm, bn], which gives a 2-D grid, and the reduction over K is a plain for loop inside each program over tiles of the inputs that the grid never sees (cutile-examples/examples/gemm.rs:20-36, 52-56). Second, hello_world has no &mut Tensor at all, so there is nothing to infer from and it must call .grid; leave that out and the launcher says error: Launch grid required. (tile_kernel.rs:1219).

What is underneath

The line across the middle of this figure is the whole point. Above it is what you write and what you can index. Below it is what the Tile IR compiler decides, and the book is careful to say it may decide differently per architecture: a tile block maps to "one or more underlying CUDA execution units (thread blocks, clusters, or warps)" (glossary.md:37-39). The three hidden layers are therefore drawn side by side, not stacked, because the source does not promise an ordering.

Evidence, all from files in this repo:

  • The Tile IR for hello_world contains get_tile_block_id and get_num_tile_blocks and no operation that names a thread, a warp, a lane, or a barrier (the dump, lines 4 to 65).
  • cutile/src exposes no warp or thread operation at all. A grep for warp, threadIdx, shfl, and syncthreads across it finds nothing.
  • The host always asks for a one-thread block: block_dim: (1, 1, 1) is a literal in the launcher generator (cutile-macro/src/kernel_launcher_generator.rs:1057), appears verbatim in the dumped launcher, and goes straight to cuLaunchKernel (cuda-core/src/api.rs:56). TileKernel::get_launch_block defaults to the same value (tile_kernel.rs:1367).
  • Threads still exist in the machine code. The kernel's second instruction is S2R R18, SR_TID.X and a predicate a few lines later branches on whether it is zero (the SASS excerpt).
  • Warps and clusters appear in this project only as tuning knobs, never as operations: occupancy, num_cta_in_cga, and num_worker_warps_per_cta in the entry's optimization hints (cutile-book/guide/performance.md:126-141).

The book says both, at two levels

"a tile program has no visible internal threads; it loads tiles, computes on them, and stores results."the programming model: cutile-book/reference/glossary.md:35
"Tiles are register-resident and processed in parallel by all threads in a warp/block."the implementation: cutile-book/reference/dsl-api.md:190

Both are true. The first is what your code can see; the second is what the compiler does with it. Keep the levels apart and neither sentence contradicts the other.

One honest limit. A SR_TID.X read proves the concept of a thread exists in the generated code; it does not prove that more than one thread ran for that launch, because the surrounding pattern is the standard "only lane zero takes the lock" preamble that device-side printing emits regardless. Settling it would need a run on a pod, and the pod is stopped.

Where this picture stops

There is no robot for the threads inside a program. A robot is one worker. A tile program is not: underneath, the compiler may spread one tile across the 32 lanes of a warp, across several warps, or across the blocks of a cluster, and may choose differently per architecture (glossary.md:37-39). Do not reach for "the robot has 32 hands"; that implies a fixed number you could count and address, and nothing in cutile/src lets you name a lane. The robot's insides are not modelled, on purpose.

There is no queue at the door. Relative order is unspecified and "kernels must not depend on one tile block running before another unless an explicit synchronization mechanism exists outside the kernel" (useful-mental-models.md:46). The first note recorded two different finishing orders from the same binary, minutes apart.

A robot is not guaranteed a body to itself. Several tile programs can be resident on one SM at once when registers and shared memory allow (glossary.md:57-59). The warehouse has no cousin for two robots sharing a chassis.

The dispatcher is not one person. Once .await is involved, the host has its own fleet: four streams, a reactor thread, and a per-thread lock. That is the next section, and it is the part the warehouse serves worst.

The other fleet: threads on the host

"Thread related" has a second half that lives entirely on the CPU. A stream is an in-order queue of GPU work; work on one stream runs in sequence, and separate streams may overlap (glossary.md:160-162). The default scheduling policy rotates over four streams, and a chain built with .then() stays on one stream so it always runs in order (cuda-async/README.md:85-104). None of that pins a stream to an OS thread. What is per-thread is the waiting, the lock, and the default device.

Glossary

GPU side

tile gpu
A multi-dimensional array fragment in registers during execution, the unit of computation; Tile<E, const D: [i32; N]> covers ranks 0 through 6. You never manage the registers or the shared memory behind it (glossary.md:7-9, 103-109).Cno direct cousin; the sub-array a block would index by hand, plus the __shared__ staging you would write
tensor gpu
A multi-dimensional array in global memory, passed as a kernel argument; no direct arithmetic, data is loaded into tiles first. Host-side its shape is a plain list, so the rank is whatever you allocated (glossary.md:11-13, tensor.rs:745-752).Ca float* and the shape you carry beside it
partition gpu
Dividing a tensor into equally sized sub-regions, one per tile block. Host-side for mutable outputs, where it also fixes the grid; device-side for shared inputs, where the same tensor can be cut different ways (glossary.md:15-31).Cthe tiling loop you write by hand
tile program, tile block, tile thread gpu
Three names for one unit: one instance of the kernel, "running once as a single logical thread of execution", with no visible internal threads. The compiler maps it to one or more thread blocks, clusters, or warps (glossary.md:33-43).Cclosest cousin: a thread block, indexed by blockIdx
launch grid host
The three-axis arrangement of tile blocks, either given with .grid / .const_grid or inferred by ceiling division from a partition; const_grid also enters the JIT cache key and gives program_id static bounds (tensor.rs:798-841, tile_kernel.rs:1350-1352).Cdim3 grid, read back as gridDim
program_id, num_programs gpu
This program's index along an axis and the extent of that axis; 0 <= program_id(k) < num_programs(k); axes above 2 fail a device assertion. Tuple forms: get_tile_block_id(), get_num_tile_blocks() (_core.rs:1598-1656).CblockIdx.x and gridDim.x
partial edge tile gpu
The last tile on an axis the tile size does not divide. It still gets a block; its out-of-range lanes read as zero (load_tile passes padding::Zero, _core.rs:3463-3484) and stores past the end are dropped (slice_non_divisible.rs:245).Cthe if (i < n) guard at the top of a kernel
GridBound, partition_prefix host
A binding's constraint on the grid: Exact by default, AtMost per axis when you opt in with partition_prefix, so a launch may cover a prefix of the blocks and the rest keep their contents (tensor.rs:269-278, 1817-1827).Cnone; you launch a smaller grid and nothing checks you
thread gpu
One lane of execution on the hardware. cuTile exposes no operation that names one, though the SASS still reads SR_TID.X.CthreadIdx
warp gpu
"A group of 32 GPU threads that execute instructions in lockstep. Warps are the smallest scheduling unit on an SM." In cuTile it appears only as the num_worker_warps_per_cta hint (glossary.md:168-170, performance.md:133).Ca warp; __shfl_sync, __ballot_sync
cluster (CGA) gpu
A group of thread blocks that can share data across SMs; in cuTile only the num_cta_in_cga hint, and in the SASS the SR_CgaCtaId read. Not to be confused with the DSL's const generic arrays, which the docs also abbreviate CGA (performance.md:130, ARCHITECTURE.md:400-405).Ca thread block cluster
SM gpu
The streaming multiprocessor, with its own registers, shared memory, and Tensor Cores; tile blocks are scheduled onto SMs by hardware, several per SM when resources allow (glossary.md:57-59).Cthe same thing
occupancy gpu
The ratio of active warps to the maximum an SM supports, driven by register and shared-memory use; also an optimization hint name (glossary.md:164-166).Cthe same thing
concurrent vs parallel gpu
Concurrent means independently in progress, in any order; parallel means at the same time on different SMs. A launch is both, and the book maps the distinction onto the Rust book's chapter 17 (glossary.md:45-55).Cthe same distinction, rarely spelled out
