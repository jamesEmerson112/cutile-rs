hello_world, Annotated

What every word in cutile-examples/examples/hello_world.rs means, and where each one lives on the trip from a Rust file to a line printed by a GPU. Every excerpt marked "real" was produced on the RunPod pod (RTX PRO 4000 Blackwell, compute capability 12.0) with the grid set to (2, 2, 1). Comparisons lean on C and CUDA C, since that is the language the GPU world grew up in.

  1. 1
    attribute, procedural macroAnything written #[...] above an item is an attribute. This one names a procedural macro in the cutile crate: a Rust function that runs inside the compiler, receives the whole module below it as tokens, and hands back rewritten Rust. What rustc compiles is the rewritten version. CClosest is __attribute__((..)) for the syntax, and #define for the rewriting, except a C macro is textual paste before the compiler runs, while this one runs inside the compiler on parsed tokens.
  2. 2
    mod, the boundaryIn plain Rust a module is a namespace and a privacy unit. Here it also draws the line the macro needs: inside is GPU code the macro owns, outside is ordinary host Rust. A module is the largest item an attribute can attach to, which is why cuTile asks for one. CC has no modules; the nearest thing is one .c file with static for private functions and a header for the public ones.
  3. 3
    scoped importsThe GPU ops come in here, so program_id means the GPU op inside the module and nothing outside it. The JIT also reads these use lines to learn which cuTile modules the kernel depends on. CAn #include that only applies inside one block, which C cannot express.
  4. 4
    entry marks the kernelThis function runs on the GPU. The macro also generates a host-side launcher with the same name. print_ir = true prints the Tile IR the JIT produces at the first launch, which is the block that scrolls past before the hello lines. C__global__ void hello_world_kernel() in CUDA C.
  5. 5
    which copy am IEvery program runs this same body and asks for its own index on each of three axes. num_programs returns the grid size on that axis. In the GPU machine code these become reads of the SR_CTAID hardware registers (see the cubin stage below). CblockIdx.x and gridDim.x.
  6. 6
    a print that runs on the GPUA macro that lowers to the print_tko Tile IR op. The GPU formats and emits the line itself, which is why the lines arrive in scheduling order, not source order. CDevice-side printf in CUDA C.
  7. 7
    importing the launcherThis brings in the generated launcher function, not the kernel body. Same name, different thing: the kernel body only ever runs on the GPU. Cnvcc does the same trick silently: a host stub with the kernel's name is what you actually call.
  8. 8
    streamA queue of GPU work. Launches placed on one stream run in order, and syncing a stream waits for everything queued on it. CcudaStream_t from cudaStreamCreate.
  9. 9
    build, do not runCalling the launcher builds a description of a launch on the CPU, a struct with the grid and options filled in step by step. Nothing has touched the GPU yet. CFilling in a struct of launch parameters before calling cudaLaunchKernel.
  10. 10
    gridHow many copies of the kernel to run, as a box with three axes. (2, 2, 1) is four programs. (1, 1, 1) is the original example. CThe first number inside <<<grid, block>>>.
  11. 11
    submit and waitQueues the launch on the stream and blocks until it finishes. The first time through, this is the moment the JIT compiles the kernel; every later launch of the same kernel reuses the cached result. CThe launch plus cudaStreamSynchronize(stream), except CUDA C compiled the kernel long before this point.

The Rust in main, line by line

Everything in main is ordinary Rust. This is the part of the file that transfers to every Rust project you will ever write, so it gets its own pass. The MIR excerpts are real: they are what rustc built from these lines on the pod.

use cuda_core::Device;

A use brings a name into scope by its path. The path is a chain of namespaces separated by ::, here the crate cuda_core and the type Device inside it. Paths are about namespaces, not files, which is why line 37 can import from a module defined in this same file.

C#include pulls in whole headers and everything lands in one global namespace; Rust imports one name at a time and keeps the crate prefix available.

fn main() -> Result<(), Error> {

Result is an enum with two variants: Ok(value) or Err(error). Returning it from main means the program can fail with a typed error and the runtime prints it. The () is the unit type, Rust's "nothing here", so Ok(()) at the bottom is "finished, nothing to return".

Cint main() returning 0 or an error code, except the compiler will not let you forget to look at the code.

let device = Device::new(0)?;

The question mark is the try operator. If the call returned Err, the function returns that error immediately, converting it into main's error type on the way; otherwise the Ok value is unwrapped into device. MIR shows exactly that: a call, a branch, a switch on which variant came back, and on the error path a conversion via from_residual.

    _3 = cuda_core::Device::new(const 0_usize) -> [return: bb1, unwind continue];
}
bb1: {
    _2 = <Result<Arc<Device>, DriverError> as Try>::branch(move _3) -> [return: bb2, unwind continue];
}
bb2: {
    _4 = discriminant(_2);
    switchInt(move _4) -> [0: bb4, 1: bb5, otherwise: bb3];
}

    _0 = <Result<(), Error> as FromResidual<..>>::from_residual(copy _5) -> [return: bb19, unwind continue];
}

The value that comes back is an Arc<Device>, visible in the MIR locals as _1: std::sync::Arc<cuda_core::Device>. An Arc is a shared, reference-counted pointer that is safe to hand across threads; the device handle is freed when the last holder drops it.

C? is the if (err != cudaSuccess) return err; you would write after every CUDA call, done for you. Arc is a pointer plus a reference count you never have to maintain by hand.

let launcher = hello_world_kernel(); launcher.grid((2, 2, 1)).sync_on(&stream)?;

This is the builder pattern. The generated launcher is a plain struct, and grid takes it by value (mut self), sets a field, and returns it, so calls chain. This is the real generated code the macro wrote for this file:

pub struct HelloWorldKernel<DI: DeviceOp<Output = ()>> {
    _const_grid: bool,
    _grid: (u32, u32, u32),
    input: Option<DI>,
    function_generics: Option<Vec<String>>,
    _phantom: std::marker::PhantomData<()>,
    _compile_options: CompileOptions,
    _compile_only: bool,
}
impl<DI: DeviceOp<Output = ()>> TileKernel<(), DI, ()> for HelloWorldKernel<DI> {
    fn grid(mut self, grid: (u32, u32, u32)) -> Self {
        self._grid = grid;
        self._const_grid = false;
        self
    }
    ..
}

Because grid consumes the launcher, the name launcher is moved and cannot be used again after line 43. That is ownership: one owner at a time, and the compiler tracks the handoff. &stream is different: it lends the stream for the duration of the call and keeps ownership on line 41. The tuple (2, 2, 1) becomes three constants in MIR, (const 2_u32, const 2_u32, const 1_u32).

CIn C you would fill a struct and pass a pointer; nothing stops you from using it again after a function consumed it. &stream is a pointer whose lifetime the compiler checks.

Ok(()) }

When main ends, the stream and then the device go out of scope and are dropped, in reverse order of creation. You wrote no cleanup; rustc inserted it. MIR shows the calls it added:

}
bb17: {
    drop(_1) -> [return: bb19, unwind continue];  // _1 is `device`

CThe cudaStreamDestroy you have to remember, on every exit path including the error ones. The unwind edges above are those error paths, generated for you.

Two compilers, one module

The module is compiled twice by two different compilers. rustc compiles it as host code, to check it and produce the launcher. The cuTile JIT compiles it as GPU code when the program runs. The Windows box can do the whole top lane; only the pod can do the bottom one. Click any stage, or step through with the buttons. Each stage shows what it produced for this exact file.

Same shape, three owners

rustc's stages, the cuTile JIT's stages, and CUDA C's stages line up one for one. An intermediate representation, IR for short, is a simplified internal language a compiler uses because it is easier to analyze than raw source. Every column below has one.

Bytecode here is not Java bytecode

Java's .class files are bytecode that the Java virtual machine executes. cuTile's bytecode is never executed. It is the Tile IR you can read, encoded compactly so tileiras can read it, the way PTX text is handed to ptxas in CUDA C, or a .o object file is handed to the linker. The GPU only ever runs the cubin. The project cares about versions 13.2 and 13.3 because a file format has to be agreed on by writer and reader.

A fleet on a grid

Picture a warehouse floor divided into cells, and a dispatcher with one instruction sheet. The dispatcher hands the same sheet to a fleet of robots, one robot per cell. Each robot reads its own cell number off its badge, reads the fleet size off the sheet, does its job on its own patch of floor, and logs a line. The dispatcher waits at the door until every robot is back.

That is a kernel launch. The instruction sheet is the kernel (hello_world_kernel). The fleet is the grid (.grid((2, 2, 1))), and each robot is one program. The badge is program_id, the fleet size is num_programs, and the patch of floor is that program's tile: disjoint by construction, so no two robots ever work the same square. The door the dispatcher waits at is .sync_on(&stream). Robots do not finish in a fixed order, so the log lines arrive in whatever order the fleet produced them. Glossary

  

    
attribute build
A note attached to an item with #[...]. Some are read by rustc itself, like #[allow(..)]; some name a macro that rewrites the item.C__attribute__((..)), #pragma

    
procedural macro build
A Rust function that runs inside the compiler and transforms tokens into other tokens. cutile::module and cutile::entry are both proc macros from the cutile-macro crate.C#define, but on parsed tokens rather than raw text, and type-checked afterwards

    
mod build
A module: a named namespace and the unit of privacy. Items are private to their module unless marked pub. Written inline as mod name { .. } or as mod name; pointing at a file.Ca translation unit with static for private and a header for public

    
kernel gpu
A function that runs on the GPU, launched from the CPU and executed by many programs at once. Not the operating-system kernel and not a convolution kernel; the three share a word and nothing else.C__global__ function

    
program gpu
One running copy of a kernel, identified by its coordinates in the grid.Ca thread block, indexed by blockIdx

    
grid host
The number of programs to launch, as a box with three axes. Each axis is at least 1, and unused axes stay at 1.Cdim3 grid, read back as gridDim

    
tile gpu
A small block of an array, the unit of data cuTile hands to each program. Every program gets a disjoint tile, which is what makes launch order irrelevant.Cno direct cousin; the slice of an array a block would index by hand

    
launcher host
The host-side struct and function the macro generates for each entry, under the kernel's own name. Calling it builds a launch description; .grid and .sync_on finish it.Cthe host stub nvcc generates behind <<< >>>

    
stream host
An in-order queue of GPU work owned by the host. Work on one stream runs in sequence; separate streams may overlap.CcudaStream_t

    
ahead-of-time compilation build
Turning all code into machine code before the program starts. That is what cargo build does for the host side.Cwhat gcc, clang, and nvcc always do

    
JIT host
"Just in time": a compiler that runs while the program is executing, producing machine code right before it is needed. cutile-compiler does it for kernels at the first launch.CNVRTC, which compiles CUDA C source strings at run time; also the driver's own PTX JIT

    
IR buildhost
Intermediate representation: a compiler's internal, simplified language between source and machine code. Both rustc and the JIT have several.CGIMPLE in gcc, LLVM IR in clang, PTX in nvcc

    
HIR build
rustc's high-level IR: Rust after macro expansion and name resolution, with sugar like for and ? desugared. Type checking runs on it.Cthe compiler's AST after preprocessing (gcc -E shows the input to it)

    
MIR build
rustc's mid-level IR: functions as graphs of basic blocks with explicit temporaries, borrows, and drops. The borrow checker runs on it. Stable rustc can dump it with --emit=mir.CGIMPLE is the same shape, minus the borrow checker

    
LLVM IR build
The input language of LLVM, a compiler backend shared by rustc, clang, Swift, and others. rustc translates MIR to it and lets LLVM optimize and emit machine code.Cidentical: clang -S -emit-llvm produces the same language

    
Tile IR host
NVIDIA's intermediate language for tile-based GPU programs, and the contract between this project and NVIDIA's tools. The cutile-ir crate builds it in pure Rust.CPTX plays this role for CUDA C

    
bytecode host
The binary encoding of a Tile IR module, written by cutile-ir and read by tileiras. Versioned 13.2 or 13.3 to match the toolkit.Can object file: a binary you hand to the next tool and never read

    
tileiras host
NVIDIA's Tile IR assembler, shipped in CUDA 13.2 and later. The JIT runs it as a subprocess to turn bytecode into a cubin.Cptxas

    
cubin gpu
A CUDA binary: an ELF file holding SASS, the machine code of one GPU generation. Loaded into the driver with cuModuleLoadData.Cthe same file nvcc produces; inspect either with cuobjdump -sass

    
SASS gpu
The GPU's native instruction set, what a cubin contains. S2UR UR4, SR_CTAID.X is how a program learns its own index.Csame thing; x86 assembly is the host-side analogue

    
compute capability gpu
The GPU generation a cubin targets, written sm_NN. cuTile needs sm_80 or newer; the pod is sm_120 and the Windows GTX 1070 Ti is sm_61.Cnvcc -arch=sm_120

    
kernel cache host
Compiled kernels kept in memory per process, keyed by specialization, so only the first launch pays for the JIT. An optional on-disk cache, keyed by the bytecode's hash, is opt-in with jit_cache::enable_default().Cthe driver's PTX JIT cache under ~/.nv/ComputeCache
